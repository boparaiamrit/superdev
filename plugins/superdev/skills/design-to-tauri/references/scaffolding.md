# Scaffolding a Tauri 2 client in the monorepo

## Layout

```
apps/mobile/
  package.json            # name @<scope>/mobile; scripts: dev, build (tsc --noEmit && vite build), typecheck, lint, tauri
  index.html  vite.config.ts  tsconfig.json  components.json
  src/
    main.tsx  app/ (router, providers, live-update wiring)
    lib/ (api.ts, session.ts, config.ts, realtime/, query-keys.ts)
    modules/<area>/ (api.ts, components/, hooks/, pages/)   # same module law as the web app
    components/ui/          # shadcn primitives
  src-tauri/
    Cargo.toml  tauri.conf.json  tauri.dev.conf.json  build.rs
    capabilities/default.json  capabilities/dev.json   # release set; debug-only origins (security.md §2)
    src/lib.rs  src/main.rs
    gen/android/            # generated by `tauri android init`, then edited — commit it
    gen/apple/              # generated on a Mac by `tauri ios init` — commit it
  qa/                       # device evidence, gitignored
```

`build` is the frontend build `verify-done.mjs` runs for every package; APKs come from `tauri android build`, never from `build`.

The client imports `@<scope>/contracts` exactly like the web app. A CommonJS contracts build ships the whole of zod into the bundle — acceptable inside an app bundle; do not fork the contracts into the client to save size.

## Creating it

Use the official template, then move it into `apps/mobile` and align it with the workspace:

```bash
pnpm create tauri-app        # React + TypeScript + Vite; pick the workspace package manager
cd apps/mobile && pnpm tauri android init      # any OS with the Android toolchain
# on a Mac only:
pnpm tauri ios init
```

Set in `tauri.conf.json`: `identifier` (reverse DNS, permanent once published), `productName`, `version`, `build.devUrl` (Vite dev port, fixed with `strictPort`), `build.frontendDist` (`../dist`), the app window, and `app.security.csp` (see `security.md`).

Vite: a fixed port (e.g. 1420, `strictPort: true`), `envPrefix: ['VITE_', 'TAURI_ENV_']`, `server.host` from `TAURI_DEV_HOST` for phones on the LAN, and a `/api/v1` proxy to the local API for browser-only UI work.

## Dependencies

- Pick **exact** versions at least two weeks old. Every Tauri plugin is a pair — the Rust crate in `Cargo.toml` (`tauri-plugin-http = "=2.x.y"`) and the npm package (`@tauri-apps/plugin-http` `2.x.y`). Keep each pair on the same version and all of them within the same `tauri` 2.x line.
- Register each plugin in `src/lib.rs` (`.plugin(tauri_plugin_http::init())`) **and** grant only the permissions you use in `capabilities/default.json`.
- Typical set: `http` (API), `store` (non-secret preferences), `stronghold` or a keystore plugin (secrets), `opener` (tel:, mailto:, wa.me, the web app), `os` (platform). Add `barcode-scanner` (QR sign-in, phones only), `notification` (phone alerts), `deep-link` only when a feature needs them.
- Before pinning a plugin, read its changelog for open mobile bugs (scanner cancel, notification payloads) and record any workaround next to the code with the version it applies to.

## Android toolchain (Windows, macOS, Linux)

- **Windows first:** Microsoft C++ Build Tools ("Desktop development with C++"), WebView2 (built into Windows 11), and Rust's MSVC toolchain. If `tauri android build` fails creating a symbolic link, turn on Developer Mode (it grants symlink creation) and rebuild.

- JDK 17 (Android Studio's bundled JBR works), Android SDK (platform 34+, build-tools, platform-tools, emulator), NDK 27-class.
- Environment: `ANDROID_HOME` (and `ANDROID_SDK_ROOT`), `NDK_HOME` (`$ANDROID_HOME/ndk/<version>`), `JAVA_HOME`.
- Rust targets: `rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android`.
- An emulator image matching the host architecture (x86_64 on Intel/AMD, arm64 on Apple Silicon) with Google APIs; enable hardware acceleration (`-accel on`; WHPX/HAXM on Windows).
- Builds: `pnpm tauri android build --debug --apk --target x86_64` for the emulator (fast), all ABIs for phones. A debug APK is large because the Rust library keeps debug info; release builds are a fraction of that.

## Generated Android project — edits to keep

`tauri android init` writes `src-tauri/gen/android`. Commit it and keep these edits (re-apply them if you regenerate):

- **Insets.** Android 15 forces edge-to-edge; an edge-to-edge window is not resized for the keyboard, and older System WebViews only report the cutout through `env(safe-area-inset-*)`. Add a window-insets listener in `MainActivity` that pads the content view by status bar + cutout + navigation/gesture bar + IME. Without it the bottom tab bar sits under the gesture bar and bottom sheets sit under the keyboard.
- **System bars.** Choose light/dark system-bar icons explicitly for the app theme; do not leave them to the system theme.
- **Camera from `<input type="file" capture>`.** Android 11+ package visibility hides the camera app unless the manifest has `<queries><intent><action android:name="android.media.action.IMAGE_CAPTURE"/></intent></queries>`.
- **Back button.** Wire Android back to the app's own stack (close sheet → previous screen → home tab → exit). The WebView's history alone is unreliable: entries pushed without a user gesture inside the page are skipped.
- **Theme and icons.** Window background in the app colour (no white flash), adaptive icon background, notification small icon (monochrome vector) kept in release builds.
- **Cleartext.** Allow cleartext HTTP only in the debug manifest/network-security config (the local API is plain HTTP); release must not.

## iOS

Builds need macOS + Xcode. On any OS you can prepare: identifier, display name, icons (`src-tauri/icons/ios`), minimum iOS version, `src-tauri/Info.ios.plist` usage strings for every permission used (camera, photo library, notifications), and `NSAllowsLocalNetworking` for the simulator to reach the local API. On the Mac: Rust iOS targets, CocoaPods, `tauri ios init`, open the Xcode project, choose the signing team, `tauri ios dev`.

## Configuration pattern

One rule for the API origin, in `src/lib/config.ts`:

1. a hidden in-app switch for testers (debug builds), restricted to origins the HTTP capability allows;
2. a build-time `VITE_API_ORIGIN`;
3. a platform default: Android emulator `http://10.0.2.2:<port>`, iOS simulator and desktop `http://localhost:<port>`.

Media and links the API returns as relative paths are prefixed with the API origin. Public links that must open in a browser use the canonical public-site origin (hard-rules #11), opened with the opener plugin.
